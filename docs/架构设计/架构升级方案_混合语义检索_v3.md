## 零、商业规划对齐

> **设计原则**：架构决策必须服务于商业目标，技术选型必须支撑盈利模式。

### 0.1 商业目标到架构决策的映射

| 商业目标（来自商业价值评估报告） | 架构决策 | 实现方式 |
|------|------|------|
| **检索质量是生命线**（8.1 必须做好第一件事） | MedCPT 语义精排 + Cross-Encoder 重排序 | 两段式混合检索，NDCG@10 目标 > 0.65 |
| **专业信任是护城河** | 所有结果标注 PMID/DOI，AI 输出可溯源 | Article 模型强制保留 pmid/doi 字段 |
| **轻量化与高性价比**（竞争优势一） | LanceDB 嵌入式 + Streamlit 单文件部署 | 零运维成本，普通 PC 即可运行 |
| **开源可控与定制化**（竞争优势三） | 模块化 search/ 包，组件可插拔 | 每个模块独立，支持机构二次开发 |
| **私有化部署选项**（机构版需求） | 无外部服务依赖（SQLite + LanceDB + 本地模型） | 一键私有化，满足数据安全要求 |
| **快速验证 PMF**（阶段一目标） | Phase 1 聚焦核心语义检索，4 个模块即可跑通 | 最小可用版验证检索效果提升 |
| **合规安全是底线**（8.1 必须做好第四件事） | 数据最小化 + API Key 加密 + 免责声明 | 不存储原始文献全文，仅缓存向量 |

## 一、问题诊断与升级目标

### 1.1 当前系统的根本缺陷

当前 `search_pubmed()`（[app.py#L345](file:///d:/trae/项目16：接单/a6_医学PubMed检索/streamlit/app.py#L345)）的检索流程：

```
用户关键词 -> esearch(term=keyword, sort=relevance) -> efetch -> 文献列表
```

| 缺陷 | 原因 | 后果 |
|------|------|------|
| 无语义理解 | 关键词原样传入，不理解研究意图 | "化疗后中性粒细胞减少的预测因子"搜不出用 monocyte count 预测 FN 的文献 |
| 无 MeSH 映射 | 自然语言未转受控词汇 | 漏掉标引了 MeSH 但标题/摘要不含该词的文献 |
| 无语义排序 | 仅靠 PubMed 默认 relevance | 语义相关但关键词不同的文献排在后面 |
| 无相关性精排 | 无 query-document 语义匹配 | 无法区分"关键词命中但主题无关"与"真正相关"的文献 |
| 无效果度量 | 无评估指标 | 无法量化检索质量，无法持续优化 |

### 1.2 升级目标

| 目标 | 衡量标准 |
|------|---------|
| 精准理解研究意图 | 用户自然语言输入 -> 系统自动拆解为结构化概念 + MeSH + 语义向量 |
| 语义级精准匹配 | 引入 MedCPT 语义编码，计算 query 与文献摘要的语义相似度 |
| 检索效果可量化 | NDCG@10、Precision@10、Recall@K 可测量、可对比、可优化 |
| 商业化可部署 | 模块化架构，支持从单机原型到云服务的平滑扩展 |
| 优雅降级 | 语义层失败时回退到 v2.1 的 MeSH+Boolean 检索，不中断服务 |

## 二、技术调研结论

### 2.1 前沿参考：LitSense 2.0（NLM/NII 官方，2025）

NLM（美国国家医学图书馆）官方的 LitSense 2.0 确立了生物医学检索的黄金范式：

```
用户查询 -> BM25/IDF 召回 Top-K -> MedCPT 语义重排序 -> 精排结果
```

- 覆盖 3800 万 PubMed 摘要 + 660 万 PMC 全文
- 使用 **MedCPT** 生物医学文本编码器生成语义向量
- 混合词法 + 语义分数线性组合重排序
- 评估指标：NDCG、MAP

**本方案以此范式为理论基础**，适配到本项目的"PubMed 远程召回 + 本地语义精排"约束。

### 2.2 GitHub 开源工具调研结论

| 层次 | 推荐方案 | 备选 | 选用理由 |
|------|---------|------|---------|
| **语义编码** | MedCPT (NCBI) | PubMedBERT, BioLinkBERT | MedCPT 专为生物医学 passage retrieval 训练，是 LitSense 2.0 的同款模型，query-article 对比学习优化 |
| **向量存储** | LanceDB | Qdrant, FAISS, ChromaDB | 嵌入式无需独立服务，原生支持向量+BM25 混合检索，适合 Streamlit 单机部署；Qdrant 适合后续云化 |
| **重排序** | bge-reranker-v2-m3 | cross-encoder/ms-marco, pygaggle | 567M 参数，中英双语，BEIR 表现优秀；pygaggle 有 TREC-COVID 验证但偏学术 |
| **检索框架** | 自建轻量管道 | Pyserini, BEIR | Pyserini 依赖 Java/Lucene，部署复杂；自建管道用 sentence-transformers + LanceDB 更轻量 |
| **评估框架** | BEIR 数据集 + 自建标注集 | — | TREC-COVID/NFCorpus 做基线对比，.nbib 案例做真实场景验证 |
| **查询理解** | DeepSeek LLM（已有） | — | 复用现有 DeepSeek 集成，做概念拆解 + MeSH 映射 |
| **文献获取** | Biopython Entrez | requests（现有） | Biopython 封装更完整，但现有 requests 方案已够用，保持不变 |

### 2.3 关键技术选型论证

**为什么选 MedCPT 而非 PubMedBERT？**
- MedCPT 是 contrastive learning 训练的 query-article 双编码器，直接优化"查询-文献"匹配任务
- PubMedBERT 是通用生物医学 NLP 模型，需额外适配才能用于检索
- MedCPT 被 NLM 官方产品 LitSense 2.0 采用，经过大规模验证
- HuggingFace 可直接加载：`ncbi/MedCPT-Query-Encoder` + `ncbi/MedCPT-Article-Encoder`

**为什么选 LanceDB 而非 Qdrant？**
- LanceDB 是嵌入式（类似 SQLite 之于 PostgreSQL），无需独立服务进程
- 原生支持向量检索 + BM25 全文检索的混合查询
- Streamlit 单机部署零额外运维
- 后续商业化云化时可平滑迁移到 Qdrant

## 三、新架构设计：两段式混合语义检索

### 3.1 设计理念

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                   │
│   Tier 1: 结构化召回（远程）          Tier 2: 语义精排（本地）      │
│                                                                   │
│   PubMed 3800万文献全库              候选池 50-100 篇              │
│   esearch + MeSH Boolean            MedCPT 语义编码 + 重排序      │
│   目标：高召回，不漏相关文献          目标：高精度，精准排序        │
│   延迟：~3s                          延迟：~2-3s                  │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

**核心思路**：不试图本地索引全部 PubMed（3800万篇不可行），而是用 PubMed 远程检索做第一段召回（利用其全库覆盖 + MeSH 标引优势），再在本地对候选池做语义精排（补足 PubMed 不理解自然语言意图的短板）。

### 3.4 核心流程详解

#### Step 0：意图理解（query_understanding.py）

```
用户自然语言研究问题
  例："化疗后中性粒细胞减少的血液学预测因子"
        ↓
  ┌──────────────────────────────────────────┐
  │  0.1 LLM 概念拆解（DeepSeek）             │
  │  输出结构化 JSON：                         │
  │  - research_intent: 研究意图一句话描述     │
  │  - concepts[]: 概念维度                    │
  │    - name, english_terms,                  │
  │      mesh_candidates, synonyms             │
  │  - pico: P/I/O/C 元素（如可识别）          │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  0.2 MeSH 术语验证与扩展（并行+缓存）      │
  │  - MeSH REST API 验证候选词               │
  │  - 获取 tree_numbers, entry_terms,        │
  │    subheadings                            │
  │  - 缓存到 SQLite mesh_cache               │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  0.3 双轨查询生成                         │
  │  - Boolean 检索式（给 Tier1 用）           │
  │    宽/中/窄三档自适应                     │
  │  - 语义查询文本（给 Tier2 用）             │
  │    将 research_intent + concepts 拼为     │
  │    英文语义查询字符串                      │
  └──────────────┬───────────────────────────┘
                 ↓
  返回 SearchStrategy（含 Boolean query + semantic query）
```

#### Step 1：Tier 1 结构化召回（pubmed_recall.py）

```
  ┌──────────────────────────────────────────┐
  │  1.1 esearch（自适应档位选择）             │
  │  - 用中档 Boolean 检索式 esearch           │
  │  - retmax=0 取 total_count                │
  │  - >500 切窄档, <10 切宽档                 │
  │  - 最终 esearch retmax=50-100              │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  1.2 efetch 获取全部候选摘要              │
  │  - XML 解析为 Article 列表                │
  │  - 记录 PubMed relevance_rank             │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  1.3 elink 相关文献扩展（可选）            │
  │  - 取 Top 5 的 Related Articles           │
  │  - 合并去重，候选池扩至 ~80-120 篇         │
  └──────────────┬───────────────────────────┘
                 ↓
  候选文献池（每篇含 pmid, title, abstract, metadata）
```

#### Step 2：Tier 2 语义精排（semantic_rerank.py）-- 核心创新

```
  ┌──────────────────────────────────────────┐
  │  2.1 查询向量化                           │
  │  - 用 MedCPT-Query-Encoder 编码           │
  │    semantic_query -> query_vec (768d)     │
  │  - 单次推理，~50ms                        │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  2.2 候选文献向量化（缓存优先）            │
  │  - 查 LanceDB article_vectors 表          │
  │  - 未命中的用 MedCPT-Article-Encoder 编码 │
  │    title + abstract -> article_vec        │
  │  - 写入 LanceDB 缓存（PMID 为主键）        │
  │  - 命中缓存 ~1ms/篇，未命中 ~30ms/篇       │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  2.3 语义相似度计算                       │
  │  - cosine_similarity(query_vec,           │
  │                      article_vec)         │
  │  - 得到 semantic_score（0-1）              │
  │  - 这是"理解研究意图"的核心信号            │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  2.4 BM25 本地词法评分（补充精确匹配）     │
  │  - LanceDB BM25 over candidate abstracts  │
  │  - 捕获 MedCPT 可能遗漏的精确术语匹配      │
  │  - 得到 bm25_score                         │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  2.5 混合分数融合                         │
  │  - Reciprocal Rank Fusion (RRF):          │
  │    fused = Σ 1/(k + rank_i)               │
  │    对 semantic_rank 和 bm25_rank 融合      │
  │  - 或加权线性组合：                        │
  │    hybrid = 0.6*semantic + 0.4*bm25       │
  │  - 取 Top 10-15 进入重排序               │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  2.6 Cross-Encoder 精排                   │
  │  - bge-reranker-v2-m3 对 (query, abstract)│
  │    逐对计算精细相关性分数                  │
  │  - cross-encoder 能感知 query-doc 深度    │
  │    语义交互，比 bi-encoder 更准            │
  │  - 得到 rerank_score（0-1）                │
  │  - 仅对 Top 10-15 计算（实测 ~1s/篇 CPU）  │
  └──────────────┬───────────────────────────┘
                 ↓
  精排后的文献列表
```

#### Step 3：引文增强与综合评分（citation_boost.py）

```
  ┌──────────────────────────────────────────┐
  │  3.1 引文数据获取（缓存优先）              │
  │  - elink citedin 查 PubMed 内被引         │
  │  - 缓存 7 天                              │
  └──────────────┬───────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────┐
  │  3.2 综合评分                             │
  │  score = 0.45 * rerank_score     # 语义相关性（主导）
  │        + 0.20 * recency_score    # 时效性
  │        + 0.20 * citation_score   # 学术影响力
  │        + 0.15 * pubmed_relevance # PubMed 原始排序
  │                                        │
  │  归一化：                                │
  │  - rerank_score: cross-encoder 直接输出  │
  │  - recency_score: linear(年份)           │
  │  - citation_score: log(citations+1)      │
  │  - pubmed_relevance: 1 - rank/total      │
  └──────────────┬───────────────────────────┘
                 ↓
  按 final_score 降序排列，截取 Top N 返回
```

### 5.2 缓存策略

|------|------|--------|---------|
| MedSH 术语 | SQLite mesh_cache | 永久（年度更新） | 同主题检索复用 |

## 六、关键技术难点及解决方案

### 难点 1：MedCPT 模型部署（CPU vs GPU）

**问题**：MedCPT 约 110M 参数，CPU 推理编码 100 篇摘要约需 3-5s，可能影响用户体验。

**实测数据**（2026-07-31 验证）：
- 模型加载（首次/缓存）：~50s / ~3s
- 查询编码：0.21s（单条）
- 文献编码：0.15s/篇（批量 20 篇 3.85s）
- 语义区分度：相关 0.69 vs 无关 0.49（+40.4%）

**解决方案**：
- **阶段一（原型）**：CPU 推理 + 向量缓存。首次慢，缓存命中后快。可接受。
- **阶段二（商业化）**：ONNX 量化加速（推理速度提升 2-3x），或部署独立 embedding 服务。
- **降级**：若 MedCPT 加载失败，回退为仅用 BM25 + PubMed relevance（v2.1 行为）。
- **国内网络**：需设置 `HF_ENDPOINT=https://hf-mirror.com` 解决 HuggingFace 连接超时。

```python
# 加载策略：懒加载 + 单例
_model_cache = {}

def get_medcpt_query_encoder():
    if "query_encoder" not in _model_cache:
        from sentence_transformers import SentenceTransformer
        _model_cache["query_encoder"] = SentenceTransformer(
            "ncbi/MedCPT-Query-Encoder", device="cpu"
        )
    return _model_cache["query_encoder"]
```

### 难点 2：LLM JSON 输出鲁棒性

**问题**：DeepSeek 概念拆解要求输出纯 JSON，实际可能包裹 Markdown 代码块或带额外说明。

**解决方案**：
```python
import json, re

def parse_llm_json(raw: str) -> dict:
    """容错解析 LLM 输出的 JSON。"""
    # 1. 剥离 Markdown 代码围栏
    cleaned = re.sub(r"```(?:json)?\s*", "", raw).strip()
    # 2. 尝试直接解析
    try:
        return json.loads(cleaned)
    except json.JSONDecodeError:
        # 3. 正则提取首个 JSON 对象
        match = re.search(r"\{[\s\S]*\}", cleaned)
        if match:
            try:
                return json.loads(match.group())
            except json.JSONDecodeError:
                pass
    # 4. 解析失败 -> 降级为原始关键词
    return {"fallback": True, "raw_keyword": raw}
```

### 难点 3：SQLite 并发写入（并行 MeSH 验证）

**问题**：ThreadPoolExecutor 并行验证 MeSH 时多线程写 SQLite mesh_cache 触发 `database is locked`。

**解决方案**：开启 WAL 模式 + 写操作加锁。
```python

_write_lock = threading.Lock()

def init_db_wal(db_path: str):

    conn.execute("PRAGMA journal_mode=WAL")
    conn.close()

def cache_mesh_term_safe(term, ui, ...):
    with _write_lock:
        # 写入操作
```

### 难点 4：评估集构建（无现成标注数据）

**问题**：要量化检索效果（Precision/Recall/NDCG），需要"查询-相关文献"标注对，但项目无现成标注。

**解决方案**：三源融合构建评估集
1. **.nbib 案例文件**：`搜索案例/` 下的 .nbib 文件是真实 PubMed 检索结果，将其对应的查询作为测试查询，结果文献作为"相关"标注。
2. **LLM 辅助标注**：对检索结果用 DeepSeek 打相关性标签（0-3 分），抽样人工校验。
3. **TREC-COVID 子集**：从 BEIR 的 TREC-COVID 数据集抽取 50 条查询作为标准化基线。

### 难点 5：候选池规模与延迟平衡

**问题**：候选池太小（漏相关文献），太大（Cross-Encoder 重排序慢）。

**解决方案**：漏斗式逐级缩减
```
PubMed esearch: retmax=50        # 召回 50 篇
elink 扩展:     +20-30 篇        # 扩展至 ~80 篇
MedCPT 相似度:  全部计算(~80)    # 快，bi-encoder
RRF 融合:       取 Top 30        # 缩减
Cross-Encoder:  仅 Top 30        # 慢，但量小
最终返回:       Top N（用户设定）
```

## 十、错误处理与降级策略

| 场景 | 降级方案 | 用户感知 |
|------|---------|---------|
| DeepSeek 意图理解失败 | 回退为原始关键词 esearch | "智能优化不可用，使用基础检索" |
| LLM JSON 解析失败 | 用原始关键词 + 自动 MeSH 查找 | "概念拆解降级" |
| MeSH REST API 超时 | 跳过 MeSH，用 LLM 候选词 | "MeSH 验证跳过" |
| MedCPT 模型加载失败 | 跳过语义精排，仅用 PubMed relevance + 引文 | "语义排序不可用" |
| LanceDB 读写失败 | 跳过向量缓存，每次实时编码 | 无感知（变慢但不报错） |
| Cross-Encoder 失败 | 跳过重排序，用 RRF 融合分排序 | "精排跳过" |
| esearch 返回 0 结果 | 自动切宽档重试 | "已扩大检索范围" |
| elink 扩展/被引失败 | 跳过对应功能 | 标注功能不可用 |
| 候选文献无摘要 | semantic_score = 0，仅用其他信号 | 标注"无摘要" |

### 14.4 数据安全设计

| 数据类型 | 存储位置 | 保留策略 | 加密 | 备份 |
|---------|---------|---------|------|------|
| 用户账号 | SQLite users 表 | 永久 | 密码 SHA-256 + salt | 每日 |

| 检索策略 | SQLite usage_log.search_strategy | 90 天 | 无 | 每日 |
| 文献向量 | LanceDB article_vectors | 永久 | 无（公开数据） | 可重建 |
| 引文缓存 | SQLite citation_cache | 7 天滚动 | 无 | 可重建 |
| MeSH 缓存 | SQLite mesh_cache | 永久 | 无（公开数据） | 可重建 |
| API Key | SQLite users（加密字段） | 用户删除时清除 | AES-256 | 加密备份 |

| 对话会话 | SQLite chat_sessions | 用户删除时清除 | 无 | 每日 |
| 对话消息 | SQLite chat_messages | 用户删除时清除 | 无 | 每日 |
| 文献摘要 | 不持久化（实时从 PubMed 获取） | - | - | - |
